# ---- 核心 -------------------------------------------------------------------
# **上界不是洁癖，是为了躲一个会让整个 job 崩掉的二进制缺陷（E-52）。**
#
# numpy 的 manylinux wheel 自带一份 OpenBLAS。从 **2.5.2** 起它换成
# **OpenBLAS 0.3.34**，而 0.3.34 的 `dgemm_kernel_HASWELL` 有一个
# **栈缓冲区越界**：内核把 k 维分块打包进一个固定 0x7080 字节的栈缓冲，
# 每步写 96 字节且对 k 无上界；k ≳ 319 时越过缓冲、覆盖 callee-saved
# 寄存器与返回地址，最后那条 `ret` 直接 SIGSEGV（上游 OpenBLAS #6026，
# 2026-09-11 报、09-13 关）。**k 的取值由 level-3 blocking 在运行期按宿主
# cache 拓扑决定** —— 所以同一份二进制在不同 runner 上时崩时不崩，
# 上游实测"受影响的机器上约三次崩一次"。这与本仓观测完全吻合：
# 同一 commit、同一批包版本、相隔 8 分钟的两个 run 一成一败。
#
# 本仓 CI 恰好把 #6026 的复现条件凑齐了：`OPENBLAS_CORETYPE: Haswell`
# + `OPENBLAS_NUM_THREADS: 1` + GitHub 托管 runner。崩溃落在
# `sc.pp.scrublet` 内部的稠密 GEMM（`_scrublet/pipeline.py:79` 先
# `.toarray()`，再交 `PCA(svd_solver="arpack")`）。
#
# 实测各 wheel 自带的 OpenBLAS（`numpy.libs/libscipy_openblas64_*.so`
# 里的版本串）：
#
#   numpy 2.4.6 → OpenBLAS 0.3.31.188.0   正常
#   numpy 2.5.0 → OpenBLAS 0.3.33.112.0   正常
#   numpy 2.5.1 → OpenBLAS 0.3.33.112.0   **最后一个正常版**
#   numpy 2.5.2 → OpenBLAS 0.3.34.0.0     回归
#   numpy 2.5.3 → OpenBLAS 0.3.34.106.0   回归（= 本仓此前浮动到的版本）
#
# 修复（OpenBLAS 0.3.35 / `develop`）**尚未进入任何 numpy wheel**
# （PyPI 上最新仍是 2.5.3），所以只能钉上界，不能等它修。
# 下界 2.1 是硬约束：`anndata 0.13` 要求 `numpy>=2.1`。
